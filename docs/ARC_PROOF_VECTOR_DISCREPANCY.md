# Finding: ARC §10.2 proof blobs do not reconcile with the pinned reference

**Status:** open · **Severity:** does not affect correctness of this crate ·
**Date:** 2026-06

## TL;DR

Every **arithmetic** value in the ARC P-256 test vectors
(`draft-ietf-privacypass-arc-crypto-01` §10.2 / `draft-arc` `allVectors.json`)
reproduces **byte-for-byte** in `tessera-arc` (see `tests/test_vectors.rs`, 8/8
passing). However, the **zero-knowledge proof blobs** (`CredentialRequest.proof`,
`CredentialResponse.proof`, `Presentation*.proof`) do **not** reproduce under
the pinned reference's own Fiat-Shamir construction.

Our Fiat-Shamir + Sigma layer is instead proven correct against the
**authoritative** Sigma Protocol test vectors
(`draft-irtf-cfrg-sigma-protocols`, `sigma-proofs_Shake128_P256.json`) — see
`tests/sigma_vectors.rs`, which verifies the official `discrete_logarithm` and
`dleq` proofs and rejects tampered ones. Those vectors exercise the *identical*
transcript machinery the ARC proofs use.

## What we verified independently

For the `CredentialRequest` proof we confirmed, using an independent pure-Python
P-256 implementation (no shared code with our Rust):

1. The **instance label** (`get_label`) we compute is byte-identical to the
   reference encoding (constraint structure + SEC1-compressed elements).
2. The **simulated commitment** `map(response) − challenge·image` is identical
   between our Rust and the independent Python — so our commitment is correct.
3. The **SHAKE128 duplex-sponge transcript** (session-id derivation under the
   `"fiat-shamir/session-id"` IV, the 64-byte `protocol_id`, absorbing the
   session id + label + commitment, then squeezing) is correct: it reproduces
   the official Sigma `discrete_logarithm` challenge `d08bc038…` **exactly**.

Despite all three being correct, hashing `(label, commitment)` for the ARC
request yields neither the stored challenge nor any near-miss.

## What we ruled out

A brute-force sweep (see the scripts referenced below) over:

- challenge squeeze length ∈ {32, 48, 64} bytes (the pinned codec uses `+16` =
  48; the current Sigma POC HEAD uses `+32` = 64 — this churn is itself
  suggestive);
- session string ∈ {`ARCV1-P256CredentialRequest`, `CredentialRequest`,
  `ARCV1-P256`, several hyphenation/order variants};
- session-id derivation ∈ {`0x00·32 ‖ squeeze(32)`, `squeeze(32)`,
  `squeeze(64)`, `sha256`, `sha512`, raw}, with/without the IV tag;
- `protocol_id` ∈ {Sigma suite name, ARC name, ARC+suffix}, padded to 64;
- absorbing vs. not absorbing the session id; label plain vs. hashed

…produced **no** combination yielding the stored ARC challenge.

## Most likely cause

The ARC draft is new (Feb–Mar 2026) and the Sigma/Fiat-Shamir POC it depends on
has been changing (e.g. the codec's challenge squeeze went `+16` → `+32`). The
committed `allVectors.json` proof blobs appear to have been generated by a
toolchain snapshot whose proof-transcript wiring differs from the pinned
submodule. The arithmetic is stable across versions (hence it matches); the
proof transcript is not.

This is an **upstream test-vector/reference inconsistency**, not a bug in
`tessera-arc`. We have not modified our implementation to chase the stale blobs,
because doing so would diverge from the authoritative Sigma spec our proofs are
correctly built on.

## How this is covered instead

| Concern | Coverage |
|---|---|
| Group/hash/issuance/presentation arithmetic | `tests/test_vectors.rs` — ARC §10.2 vectors, 8/8 byte-exact |
| Fiat-Shamir + Sigma transcript & verifier | `tests/sigma_vectors.rs` — official Sigma DL + DLEQ vectors |
| ARC proof statements (request/response) | built on the proven Sigma layer; round-trip tests land with the prover (GOAL milestone 5) |
| ARC §10.2 proof blobs | `#[ignore]`d positive tests in `tests/proof_vectors.rs`, kept so they flip green if the construction is pinned down upstream |

## Reproduction

The investigation scripts (independent Python P-256, the transcript sweeps, and
the Sigma-vector confirmation) were run during development. To re-derive:

1. Clone `ietf-wg-privacypass/draft-arc` with submodules and
   `mmaker/draft-irtf-cfrg-sigma-protocols`.
2. Confirm `diff` shows the pinned vs. HEAD Sigma differ **only** in
   `codec.sage` (`scalar_byte_length() + 16` vs `+ 32`).
3. Reproduce the Sigma `discrete_logarithm` challenge from
   `sigma-proofs_Shake128_P256.json` using the transcript in
   `crates/tessera-arc/src/sigma.rs` (matches).
4. Apply the same transcript to the ARC request statement (does not match any
   squeeze length).

## Next step

File an issue upstream against `draft-arc` to regenerate `allVectors.json`
against the current `draft-irtf-cfrg-sigma-protocols` POC, and re-enable the
`#[ignore]`d tests once the blobs are consistent.
